# 뉴스 조회/수집

이 문서는 `my-news-back`의 뉴스 목록 조회(페이지네이션)와 네이버 뉴스 수집/보강(enrichment) 로직, 그리고 GeekNews/Hacker News 커뮤니티 뉴스 수집을 다룹니다. RAG 검색은 `docs/RAG-벡터-파이프라인.md`, AI 요약은 `docs/로컬-LLM-뉴스-요약.md`를 참고합니다.

## 뉴스 소스 종류 (sourceType)

`News` 테이블에는 기사 출처 성격을 구분하는 `sourceType` 컬럼(`NewsSourceType` enum: `PRESS`/`COMMUNITY`/`BLOG`, 기본값 `PRESS`)이 있습니다.

- `PRESS`: 네이버 뉴스 검색 API로 수집한 언론사 기사. 기존 카테고리(`Category`)에 연결됩니다.
- `COMMUNITY`: GeekNews, Hacker News처럼 커뮤니티/링크 애그리게이터 성격의 글. 카테고리 개념이 없어 `categoryId`는 항상 `null`입니다.
- `BLOG`: 현재 연결된 소스는 없으며, 이후 블로그 성격의 소스를 추가할 때 사용할 예비 값입니다.

**기존 화면(홈, `/news` 목록, 카테고리 탭, 검색, RAG 의미 검색, 상세, AI 요약)은 모두 `sourceType = PRESS`인 기사만 조회하도록 필터링되어 있습니다.** GeekNews/Hacker News 기사가 이 화면들에 섞여 노출되는 일이 없도록, 아래 조회 경로에 press 필터가 명시적으로 적용됩니다.

- `NewsService.getNews` (`GET /news`, `GET /news/search`가 내부적으로 재사용): `where.AND`에 `{ sourceType: 'PRESS' }`를 항상 포함
- `NewsService.getNewsById` (`GET /news/:id`): `findFirst({ where: { id, sourceType: 'PRESS' } })`
- `NewsSummaryService.summarizeNews` (`POST /news/:id/summary`): 동일하게 `sourceType: 'PRESS'`로 조회 범위를 제한
- `NewsRagService.indexRecentNews`, `NewsRagService.semanticSearch`: 재색인 대상 조회와 벡터 검색 SQL(`JOIN "News" n ... WHERE n."sourceType" = 'PRESS'`) 모두 press로 제한
- `NewsService.fetchAndCacheNews`: press가 아닌 소스로 저장한 기사는 RAG 임베딩 색인(`newsRagService.indexNews`) 자체를 호출하지 않음 (이중 방어)

커뮤니티 뉴스는 반대로 `sourceType != PRESS`로 필터링하는 별도 API(`GET /news/community`)로만 조회할 수 있습니다. 회귀 테스트는 `my-news-back/src/news/news.service.spec.ts`, `news-rag.service.spec.ts`, `news-summary.service.spec.ts`에서 Prisma 호출 인자에 press 필터가 포함되는지 직접 검증합니다.

## 커뮤니티 뉴스 수집 (GeekNews, Hacker News)

- 어댑터: `NewsSourcesRegistry`에 등록된 `geeknews`, `hacker-news` 소스 (`src/news/sources/geeknews.source.ts`, `hacker-news.source.ts`)
- `NewsService.fetchAndCacheNews(category?, sourceId = 'naver')`가 일반화되어 `sourceId`로 소스를 선택합니다. 기존 호출부(배치, 수동 수집, 컨트롤러)는 `sourceId`를 생략하면 그대로 `naver` 카테고리 수집으로 동작해 하위 호환됩니다.
- GeekNews/Hacker News는 카테고리 개념이 없는 단일 피드이므로 `category` 인자를 무시하고, `categoryId: null` / `sourceType: 'COMMUNITY'`로 저장합니다. `NEWS_CATEGORY_SLUGS`(네이버 배치 루프가 순회하는 카테고리 목록)에는 추가하지 않았으므로 네이버 배치가 이 소스들에 대해 의미 없는 검색을 시도하지 않습니다.
- Hacker News는 `score`/`descendants`를 각각 `News.externalScore`/`News.externalCommentCount`에 저장합니다. GeekNews는 두 값 모두 제공하지 않아 `null`로 저장됩니다.
- 네이버와 달리 두 소스 모두 `skipContentCrawl = true`라 본문 크롤링(enrichment)을 수행하지 않습니다(이전 단계에서 이미 적용됨).

### 배치 스케줄

`NewsBatchService`에 소스별 cron이 등록되어 있습니다 (`ENABLE_NEWS_SCHEDULE=false`면 모두 스킵, `Asia/Seoul` 기준):

| Cron | 대상 | 주기 |
| --- | --- | --- |
| `0 * * * *` | 네이버 전체 카테고리 | 매시 정각 |
| `0 6,18 * * *` | 네이버 주요 카테고리 | 하루 2회 |
| `30 */3 * * *` | GeekNews | 3시간마다 |
| `45 */3 * * *` | Hacker News | 3시간마다 (GeekNews와 15분 간격) |

GeekNews/Hacker News는 언론사 기사보다 갱신 빈도가 훨씬 낮아(피드 상단이 시간 단위로 바뀌는 정도) 매시간 수집할 필요가 없다고 판단해 3시간 주기로 설정했습니다. 두 소스의 실행 시각을 어긋나게 배치해 같은 분에 외부 호출이 몰리지 않도록 했습니다. 각 소스 호출 뒤에는 기존 배치와 동일하게 `delay(2000)`으로 다음 호출까지 쉬어갑니다.

### 수동 수집 API

`POST /news/community/fetch`는 `NewsAdminGuard` + `RequireNewsAdminKey`로 보호되는 관리자 전용 엔드포인트입니다. 외부 API를 즉시 호출하므로 `POST /news/embeddings/reindex`와 동일한 패턴으로 `x-news-admin-key` 헤더가 필요합니다.

```json
// Request body
{ "source": "geeknews" }
```

`source`는 `geeknews` 또는 `hacker-news`만 허용됩니다. 응답은 `{ "source": "...", "savedCount": number }` 형태입니다.

## 커뮤니티 뉴스 조회 API

- `GET /news/community` — GeekNews/Hacker News의 최신 글 목록을 `publishedAt DESC, id DESC` 기준으로 조회합니다.
- 쿼리 파라미터: `cursor`(선택, 페이지네이션 커서), `limit`(선택, 기본 20, 최대 50)
- 커서 인코딩은 `GET /news`와 완전히 동일합니다 (`NewsService`의 `encodeCursor`/`decodeCursor`를 그대로 재사용하는 `getCommunityNews` 메서드). 즉 `(publishedAt, id)`를 base64url로 인코딩한 불투명 문자열이며 별도의 커서 체계를 만들지 않았습니다.
- 응답 형태는 `GET /news`와 동일한 `{ items, nextCursor, hasMore }` 구조이며, 각 항목에는 `sourceType`, `externalScore`, `externalCommentCount` 필드가 포함되어 프런트엔드가 점수/댓글 수를 표시할 수 있습니다. 언론사 기사와 달리 `categoryId`/`category`는 항상 `null`입니다.

## 페이지네이션 커서

- API: `GET /news`, `GET /news/search`
- 커서는 클라이언트 입장에서 불투명(opaque) 문자열입니다. 내부 구조를 클라이언트가 해석하거나 조합할 수 없어야 합니다.
- 정렬 기준: `publishedAt DESC, id DESC` (동시각 데이터의 안정적인 tie-break을 위해 `id`를 보조 정렬 키로 사용합니다.)
- 커서는 마지막으로 조회한 항목의 `(publishedAt, id)`를 base64url로 인코딩해 생성합니다.
- 다음 페이지 조회 시 `publishedAt < cursor.publishedAt OR (publishedAt = cursor.publishedAt AND id < cursor.id)` 조건으로 이어서 조회합니다.

### 이전 방식의 문제와 수정

과거에는 `orderBy: publishedAt desc`로 정렬하면서 `where.id = { lt: cursor }`처럼 `id`(랜덤 UUID)만으로 필터링했습니다. `id`는 `publishedAt` 정렬 순서와 무관한 값이라 다음 조건이 쉽게 발생했습니다.

- 같은 페이지 안의 일부 항목이 다음 페이지에서 중복 노출됨
- 정렬 순서상 존재해야 할 일부 항목이 조회 결과에서 누락됨

수정 후에는 `publishedAt`과 `id`를 함께 커서에 담아 정렬 기준과 필터 기준을 일치시켰습니다. 이를 통해 동일한 `publishedAt`을 가진 다수의 뉴스가 있어도 중복/누락 없이 순회할 수 있습니다.

### 잘못된 커서 처리

- 커서 문자열을 디코딩할 수 없거나(base64url 디코딩 실패, 구분자 없음, 날짜 형식이 `publishedAt.toISOString()` 형식이 아니거나, `id` 부분이 UUID 형식이 아닌 경우) 레거시 UUID로도 해석되지 않으면 `BadRequestException`(HTTP 400)을 명시적으로 반환합니다.
- 커서를 무시하고 조용히 처음부터 다시 조회하지 않습니다. 클라이언트가 잘못된 커서를 계속 사용하는 상황을 감추지 않기 위함입니다.

### 기존(레거시) UUID 커서 호환

- 새 커서 형식을 적용하기 전에 이미 클라이언트가 저장해 둔 커서는 뉴스 `id`(UUID) 원문일 수 있습니다.
- 커서가 새 인코딩 형식으로 디코딩되지 않고 UUID 형식이면, 해당 `id`로 뉴스를 조회해 `publishedAt`을 가져온 뒤 새 커서 로직과 동일한 방식으로 이어서 조회합니다.
- 해당 UUID의 뉴스가 존재하지 않으면 잘못된 커서로 간주해 `BadRequestException`을 반환합니다.

## 뉴스 수집과 본문 보강(enrichment)

- API 내부에서 사용하는 배치 로직: `NewsService.fetchAndCacheNews(category)`
- 네이버 뉴스 검색 API로 기사 목록을 가져온 뒤, 기사 원문 URL을 크롤링해 `content`/`contentHtml`/`urlToImage` 등을 보강합니다.
- 이미 저장된 뉴스에 `urlToImage`, `content`, `contentHtml`이 모두 있으면 크롤링(enrichment)을 건너뜁니다(`shouldEnrich = false`).

### 기존 본문 보존 규칙

- 다음 세 경우 모두, 기존에 저장돼 있던 `content`/`contentHtml`을 그대로 유지합니다.
  - 크롤링을 건너뛴 경우 (`shouldEnrich = false`)
  - 크롤링(HTTP 요청)이 실패한 경우 (네트워크 오류, 타임아웃 등)
  - 크롤링(HTTP 요청)은 성공했지만 페이지에서 실제 기사 본문을 찾지 못해, 메타 `description`을 그대로 재포장한 짧은 텍스트만 얻은 경우
- 마지막 항목을 구분하기 위해 크롤링 결과에 `contentExtracted`(실제 DOM 본문 추출 성공 여부) 플래그를 함께 반환합니다. `contentExtracted = false`인 크롤링 결과는 기존 본문을 덮어쓸 수 있는 "새 본문"으로 취급하지 않습니다.
- 우선순위: 실제로 추출된 새 본문(`contentExtracted = true`) → 기존에 저장된 본문 → (기존 본문도 없을 때만) 검색 API의 `description` 기반으로 생성한 본문.
- 과거에는 크롤링을 건너뛰거나 실패하면(또는 크롤링은 성공했지만 본문을 찾지 못하면) `description` 기반의 짧은 본문으로 기존의 전체 본문을 덮어써 데이터 손실이 발생했습니다. 이 문제를 수정했습니다.

## 검증

```bash
npm run test --workspace my-news-back -- news.service.spec.ts news-rag.service.spec.ts news-summary.service.spec.ts
npm run lint --workspace my-news-back -- src/news/news.service.ts src/news/news.service.spec.ts
```

`news.service.spec.ts`는 Prisma/axios/RAG 서비스 의존성을 모두 mock 처리하며, 실제 DB나 외부 API를 호출하지 않습니다. 다음 회귀 시나리오를 다룹니다.

- 동일 기사 재수집 시 이미 있는 전체 본문/HTML 보존
- 본문 크롤링(HTTP 요청)이 실패했을 때 기존 본문 보존
- 크롤링은 성공했지만 실제 기사 본문을 찾지 못했을 때(설명 기반 폴백만 생성됨) 기존 본문 보존
- 기존 본문이 전혀 없을 때만 설명 기반 본문으로 대체
- `publishedAt`이 같은 여러 뉴스가 있을 때 커서 페이지네이션이 중복/누락 없이 동작
- 다중 페이지 조회 시 `publishedAt + id` 기준 안정적 정렬과 불투명 `nextCursor` 발급
- 레거시 UUID 커서 호환, 잘못된 커서, 구조가 어긋난 커서(UUID가 아닌 id 등)에 대한 명시적 오류 처리
- 커서, 카테고리, 검색어 필터가 함께 적용될 때의 조건 조합
- **press 전용 필터 회귀**: `getNews`(커서 없음 포함 모든 조합)가 항상 `{ sourceType: 'PRESS' }`를 `where.AND`에 포함하는지, `getNewsById`가 `findFirst({ where: { id, sourceType: 'PRESS' } })`로 호출되는지, `getCommunityNews`가 반대로 `{ sourceType: { not: 'PRESS' } }`로 필터링하는지를 Prisma mock 호출 인자로 직접 검증
- `fetchAndCacheNews`가 소스별로 `sourceType`/`categoryId`/`externalScore`/`externalCommentCount`를 올바르게 저장하는지(naver→PRESS+카테고리, geeknews/hacker-news→COMMUNITY+categoryId null), press가 아닌 소스는 RAG 색인을 호출하지 않는지, 알 수 없는 `sourceId`는 외부 호출 없이 0을 반환하는지

`news-rag.service.spec.ts`의 `press-only filtering` 스위트는 `indexRecentNews`가 `sourceType: 'PRESS'`로만 조회하는지, `semanticSearch`의 raw SQL 텍스트에 `n."sourceType" = 'PRESS'` 조건이 포함되는지를 검증합니다. `news-summary.service.spec.ts`는 `summarizeNews`가 `sourceType: 'PRESS'`로 조회 범위를 제한하는지 검증합니다.
